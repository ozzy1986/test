# Дедупликация заявок

Сервис забирает «сырые» заявки из `https://test.ooobs.ru/api/orders`, нормализует телефоны,
схлопывает дубли и отдаёт результат.

**Живой URL:** https://test.ozzy1986.com/api/clients (то же самое на https://test.ozzy1986.com/)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/clients`, `/` | результат `{clients, stats}` |
| GET/POST | `/api/sync` | принудительная синхронизация с источником |
| GET | `/api/health` | состояние: есть ли данные, последняя ошибка |

## Правила

- **Телефон:** берём все цифры. 11 цифр с первой 7 или 8 → `+7` + последние 10; 10 цифр (номер без кода
  страны, например `9005551212`) → `+7` + эти 10. Всё остальное отбрасывается как невалидное:
  короче, длиннее (добавочный, два номера), 11 цифр с другим кодом страны, пусто, текст, не строка.
- **Дубли** (одинаковый нормализованный телефон): остаётся заявка с максимальным `amount`; при равных —
  с более поздним `created_at`; при полном совпадении — та, что позже в выгрузке. Заявка берётся
  целиком, поля из дублей не подмешиваются.
- `amount` сравнивается как число (строки `"5 000"`, `"1,500.50"` тоже понимаются), `created_at` — как момент
  времени (ISO 8601 с любым смещением, epoch, `ДД.ММ.ГГГГ`). Нераспознанные значения проигрывают распознанным.
- **Статистика:** `received` = `unique` + `duplicates_merged` + `invalid_dropped`.
- **Порядок клиентов** — по первому появлению телефона в выгрузке.

## Идемпотентность

Результат — чистая функция от выгрузки. Синхронизация пересчитывает всё и в одной транзакции заменяет
содержимое таблицы (`phone` — первичный ключ, параллельные синхронизации сериализует advisory lock).
Если выгрузка не изменилась (sha256 тела), база не трогается вовсе. Повторные запуски дают байт-в-байт тот же ответ.

## Устойчивость

- GET отдаётся из памяти; источник перечитывается не чаще раза в 60 с и одним потоком, поэтому
  нагрузка на нас не превращается в нагрузку на источник.
- Источник недоступен, отвечает не 200, слишком большой ответ, битый JSON, `NaN`/`Infinity`, числа
  из тысяч цифр, глубокая вложенность — последний удачный результат сохраняется и продолжает отдаваться.
- Мусор в записях (не объект, `null`, массивы вместо строк, NUL-байты, одиночные суррогаты) не роняет
  ни разбор, ни запись в Postgres, ни отдачу ответа.
- База недоступна — сервис работает из памяти; после рестарта поднимает последний результат из базы.
- Наружу только чтение; `/docs` и `/openapi.json` выключены; ошибки — JSON без трейсбэков; SQL только
  параметризованный; адрес источника задан конфигом и от запроса не зависит.
- systemd-песочница (read-only ФС, без привилегий, лимит памяти 200 МБ), uvicorn слушает только localhost,
  снаружи — Apache с TLS.

## Стек и запуск

Python 3.14, FastAPI, PostgreSQL. Код: `app/normalize.py` (разбор полей), `app/dedupe.py` (чистая логика),
`app/source.py` (загрузка), `app/store.py` (Postgres), `app/service.py` (кеш и синхронизация), `app/main.py` (HTTP).

```bash
python -m venv .venv && .venv/Scripts/pip install -r requirements-dev.txt
.venv/Scripts/python -m pytest -q        # 99 тестов, в т.ч. эталон на реальной выгрузке
.venv/Scripts/uvicorn app.main:app       # локально без базы (DATABASE_URL не задан — только память)
bash deploy/deploy.sh                    # деплой на VPS с healthcheck и автооткатом
```
